## S01. 构建注入不能“编译通过、运行时缺函数”

### 已确认的问题

[replacement.mjs](../desktop/build/replacement.mjs) 有普通字符串替换：锚点失配可能不报错。
曾在内存夹具中只改变函数声明空格，构建适配器和 JSX 解析仍通过，但 hydration 函数定义消失或保存锁没有注入。

### 固定决策

- 复用 [integrate.mjs](../desktop/integrate.mjs) 的 replaceOnce 思路，不重写整个适配层。
- 每个关键锚点必须恰好命中一次；缺失、重复、顺序异常都 fail closed。
- 可把共享断言抽到 desktop/build 下的小工具；不得复制出多份近似实现。
- 不用宽泛正则“猜测”新的上游结构，不在锚点失败时继续生成残缺代码。
- 本步不升级上游依赖，不修改用户数据。

### 实施清单

- [ ] 检查 applyDiagramState 的提取、移除、重新插入是否全部有断言。
- [ ] 检查 replacementLockRef 定义、save 的锁检查、替换接口注入。
- [ ] 检查生成代码中关键定义和调用是否匹配。

- [ ] 若抽出辅助函数，不改变当前正常输入的生成语义。

### 最小夹具与验收

| 夹具 | 预期 |

| 当前固定上游源码 | 转换及 JSX 解析成功，关键函数/锁存在 |

### 2.1 关系性质：本轮统一解释，不再增加平行真源

本轮继续沿用 reviewEvidence.kind，接受 physical、logical、inferred、unspecified。

**不额外引入一套平行的 relationType 字段。** 新增一个共享纯函数统一解释，下游不能继续各自猜测 kind 的含义。

| 原始 kind | 内部关系性质 type | 依据状态 certainty | 默认能否输出 SQL FK |
|---|---|---|---|
| physical | physical | declared | 无条件且校验有效时可以 |
| logical | logical | declared | 不可以 |
| inferred | logical | inferred | 不可以 |
| unspecified 或缺失 | unspecified | unknown | 不可以 |
| 其他非空值 | invalid | invalid | 不可以，并报校验错误 |

注意：

- declared 只表示模型作者已经声明，不表示现场数据库或生产系统已验证。
- 缺失性质的旧 JSON 不能因为名称以 fk_ 开头、字段是主键或端点类型相同，就被迁移成 physical。
- 缺失 kind 可以在规范化副本中补为 unspecified；打开旧模型本身不能造成自动保存或改写原文件。
- physical 与 condition 同时存在属于冲突，报错；不能自行删除 condition 或把关系偷偷改成 logical。
- unknown 与 logical 不混为一谈。允许阅读旧模型，界面明确“性质未声明”。
- startTableId/startFieldId 是引用侧，endTableId/endFieldId 是目标侧；四边出线与这个语义无关。
- 交换端点是模型语义修改，不是修正画面左右的手段。保留撤销，并明确它可能改变物理约束含义。

### 2.2 条件：只支持已有的声明式等值，不执行表达式

- condition.field 指向**引用侧/startTableId 所在表的字段名**，精确匹配，不跨表搜索、不模糊匹配。
- condition.value 的规范输出是非空字符串。原字符串不擅自改写大小写或去掉有意义空格。
- 兼容安全整数：0 转成 "0"，负安全整数也按十进制转换。
- 小数、不安全整数、布尔、null、对象、数组不自动转换；返回明确错误，要求调用者给出明确字符串。
- condition 对象存在但无效，与“没有条件”不是同一件事。
- 不支持 AND/OR、SQL 表达式、函数执行或 IS NULL 的自由表达式；本步不扩展条件语言。
- 条件字段不存在是错误。
- 值不在 reviewEnumValues 中只作提醒，因为它不一定是封闭值域。
- SQL ENUM 可按其封闭取值检查；SET 等复杂情况不要靠猜测报硬错误。
- 重复关系的签名必须包含规范化条件；相同端点、不同条件不是重复。
- 相同端点和相同条件仍按重复处理。
- 字段重命名时，要同步维护源表中引用该旧字段名的条件；不能留下失效条件且不提示。
- 新输入无效条件应被拒绝。旧存储中已存在的无效条件必须可见、可修复，不能被当作无条件关系合并进 Bus。
- 对旧无效关系可显示“条件无效”并隔离为单独的诊断关系；不删除其模型记录，不伪造缺失表。

### 2.3 完整文档统一验证

拟新增纯函数模块，例如 desktop/review/model-contract.mjs；名字可调整，但全项目只保留一套实现。

建议接口：

~~~text
validateModelDocument(input) -> {
  model: normalizedCopy,
  errors: [{ code, path, message }],
  warnings: [{ code, path, message }]
}
~~~

执行规则：

1. 先兼容迁移，再验证；不修改 input。
2. 同时检查表、字段、关系 ID；保留合法数字 0 ID，不统一改成字符串。
3. 检查两端表/字段、复合字段映射、基数枚举、关系性质、条件。
4. 保留 one_to_one、one_to_many、many_to_one、many_to_many 的已有读取能力。
5. 非空 fields 数组是复合映射的权威；兼容 startFieldId/endFieldId 必须与第一对一致。旧兼容字段不一致时，只在规范副本中按第一对补正并返回 warning，不能用旧单对字段覆盖整个数组。
6. 不存在 fields 的旧关系允许从旧单对字段生成规范副本；明确给出空数组则报错，不能假装数组不存在。
7. 结构检查、导入、替换、预检共用规则，不复制四份判断。
8. 文件导入/替换在 errors 非空时拒绝写入；warnings 不自动等同于失败。
9. 对已经打开的旧数据，诊断不删除关系、不自动修复业务含义。
10. 稳定错误码和 JSON 路径用于 Agent；显示文本可以中英文转换。
11. 不把“没有唯一键”一律认定为逻辑关联错误，不引入完整 SQL 方言检查器。
12. 新增参与投影/端口/评分的 helper，必须加入 layout-cache-version.mjs 的依赖指纹。

### 最小验收矩阵

- 无 kind 的旧 JSON：可规范化为 unspecified，关系仍存在，原对象没被修改。
- physical + condition：错误，不静默降级。
- 非法 kind 或非法 cardinality：错误，带 relationships[n] 路径。
- condition.value = 0：显示和保存为 "0"，不能消失。
- condition.field 不存在：明确错误。
- 相同端点、不同条件：绘图、编辑、校验均接受。
- 同条件同端点重复：诊断一致。
- 普通导入和完整替换对重复关系 ID 得到相同结果。
- 复合关系和数字 0 ID：往返不变。
- 无效导入/替换：模型、撤销栈、读取视图均不被部分覆盖。

运行现有 model-checks、conditional-relations、replace-model 测试及新增契约测试。
这一阶段不需要把全部 UI 冒烟脚本跑一遍。

## S03. 修复 SQL 导出边界

### 现状问题

[桌面导出入口](../desktop/renderer/useDesktopWorkspace.js) 把所有 references 交给上游。
MySQL 和 SQLite 路径会把条件/逻辑关系输出为同时生效的物理 FK。

### 固定决策

- 统一在导出适配边界筛选，不逐个 UI 按钮各自过滤。
- 仅输出 S02 判定为 physical、无条件且有效的关系。
- logical、inferred、unspecified 保留在 JSON/评审图，导出 SQL 时不变成 FK。
- 返回/显示被跳过的关系数量和原因；不得“什么都不说”地少输出约束。
- SQL 外键方向以引用侧/目标侧为准，不能从画面位置或 1/N 标签推断。
- 解析真实 CREATE/ALTER FOREIGN KEY 的导入路径可标记 physical；凭字段名猜出的关系不能这样标记。
- 不把所有旧 JSON 的未声明关系批量转 physical。
- 不就地过滤 snapshot.references；原模型必须保持完整。
- 全量 JSON 导出仍保留所有关系及证据。
- 本步不连接数据库，也不执行生成的 SQL。

建议抽出纯函数“生成 SQL 导出模型 + skippedRelationships”，然后复用现有各方言导出器。
不要修改 work/drawdb 生成文件来充当永久修复。

### 必测夹具

1. 一个引用字段分别按 ORDER/RETURN 等条件关联多个对象：SQL 不能生成多个无条件 FK。
2. 同一个模型混合 physical、logical、inferred、unspecified：仅 physical 出现在 FK DDL 中。
3. 包含明确 physical 复合 FK：字段顺序、方向保持。
4. 原模型 before/after 深比较一致，JSON 往返关系数量不减少。
5. 枚举、空值、表字段等非关系 DDL 没有被过滤操作误删。
6. 覆盖现有导出器支持的方言入口，至少实际执行 MySQL 和 SQLite 路径；其余方言必须共用同一筛选边界。
7. 旧模型未声明性质：给出明确跳过提示，不能声称已输出完整物理约束。
8. 导入真实 FK DDL 后再导出：物理性质和映射能够保留。

纯 Node 导出测试优先。只在导出交互提示发生变化时验证一次相关弹窗，不跑整套 UI。

## S04. Agent 预检与回执：让失败可以被自动修正

### 现状入口

- [handoff](../desktop/native/model-handoff.cjs)
- [bridge](../desktop/native/command-bridge.cjs)
- [IPC](../desktop/native/ipc.cjs)
- [preload](../desktop/preload.cjs)
- [renderer 命令处理](../desktop/renderer/useDesktopWorkspace.js)

### 4.1 预检命令

拟新增 scripts/validate-model.mjs，完成后才使用如下命令：

~~~sh
node scripts/validate-model.mjs --file examples/fulfillment.drawdb.json --json
~~~

- 读取文件、执行 S02 迁移和验证；不打开 App、不调用数据库、不修改输入文件。
- stdout 输出一个 JSON 结果；调试信息只去 stderr。
- errors 非空退出码 2；文件读取失败退出码 1；只有 warnings 时退出码 0。
- 默认不写规范化文件。若实现输出参数，必须是调用方明确指定的路径。
- 脚本不能依赖浏览器 window 或打包后的私有对象。复用契约核心，不抄写校验逻辑。
- 方言类型信息要正确传入；不能因为离开 UI 就跳过原有长度/精度检查。

### 4.2 回执格式

继续只保留最新回执，不增加历史表。保留已有 ok、targetId、sha256 字段的兼容语义，新增结构化字段：

~~~json
{
  "requestId": "caller-supplied-or-generated-id",
  "operation": "replace-model",
  "targetId": "current-model-id",
  "sha256": null,
  "status": "failed",
  "ok": false,
  "errorCode": "MODEL_VALIDATION_FAILED",
  "message": "Model validation failed",
  "errors": [
    {
      "code": "CONDITION_FIELD_MISSING",
      "path": "relationships[2].reviewEvidence.condition.field",
      "message": "Referenced predicate field does not exist"
    }
  ],
  "layoutStatus": "not_observed"
}
~~~

上述为**目标接口示例，不是当前已经支持的字段**。

固定规则：

- 请求标识在解析/读取开始前生成或接收；无效参数时仍记录本次失败，无法取得 targetId 可置空。
- pending 对应 ok:null；succeeded 对应 ok:true；failed 对应 ok:false。
- 文件不存在、文件超限、JSON 解析失败、校验失败、只读、目标不匹配、超时、写入失败均有明确终态。
- 文件读取失败时 sha256 可以为空，但不能留下旧成功回执冒充本次结果。
- Renderer 捕获的 code/path/message 必须完整经过 preload、IPC、bridge 传回，不能压缩成布尔值。
- 修改 bridge 返回类型时，逐个检查所有调用方；不能让旧代码把 {ok:false} 当真值。
- succeeded 只代表模型已提交且应用；不代表布局已完成。
- S10 前 layoutStatus 可以明确为 not_observed，禁止猜成 ready。
- 每次调用者只接受匹配 requestId 的回执；时间戳不能代替请求身份。
- 失败不自动重试，不清空模型或撤销栈，不自动切换目标模型。

### 验收

用内存 writeResult 和可控 request，不需要 UI：

- renderer 返回具体错误，最终回执同样包含该错误；
- 成功、读取失败、校验失败、目标错误、忙碌和超时都有对应 requestId；
- 新调用失败后旧成功回执不能继续被认作本次成功；
- 重复/并发请求保持现有排他规则；
- 现有安全校验仍拒绝非可信 frame；表/字段/关系的数字 0 ID 不被误丢。CLI 目标模型 ID 仍沿用既有字符串规则，不能与这些实体 ID 混淆；
- UI 普通保存/离开/导入的 bridge 调用没有因返回类型变化而改变真假判断。

运行 replace-model、workbench、security 测试和新增预检/回执测试。
由于涉及跨进程消息，可以在本阶段完成后做**一次**针对性交接验证，不逐次启动完整 UI 套件。

## S05. 字段定位与选择一致性

### 5.1 长表字段定位

问题入口：[EdaWorkspace](../desktop/eda/EdaWorkspace.jsx)、[camera](../desktop/eda/camera.mjs)、[TableContent](../desktop/eda/TableContent.jsx)。

已复现：50 字段整表高 1578，在 800×600 中整表适应后 scale 约 0.355，随后摘要模式把所有字段隐藏。

固定决策：

- 表定位可以适应整表；**字段定位必须针对字段行**。
- 拟新增 focusFieldView 或等价纯函数，使用目标行中心和附近区域作为相机目标。
- 桌面字段定位默认使用约 100% 可读比例，不把整张长表塞进一个窗口。
- 表可超出画布，通过平移查看；不靠把文字缩到不可读来完成定位。
- 当前被明确定位的字段必须可见、高亮，不能被语义摘要分支隐藏。
- 不新增表内滚动容器，本轮避免字段滚动与端口同步的第二套坐标系统。
- 仅相机变化不是布局变化，不写模型、不触发自动整理。目标字段尚未在投影中时，先进入该表的 column 范围，可命中缓存或进行一次必要布局，再按本次选择定位。

### 5.2 统一选择动作

把目录、搜索、侧栏、画布字段点击收敛到同一个字段选择入口。

目标行为：

1. 选择 tableId + fieldId；
2. 按字段映射收集全部 relationshipIds，而不是只取第一个，也不能直接取整个 net 的所有兄弟关系；
3. 字段详情保持在侧栏；
4. 按边的 refs 与 relationshipIds 的交集高亮，合法共享干线可亮，但不相关兄弟分支不能跟着亮；
5. 用户点其中一条时，再切到单关系聚焦；
6. 清除选择时清理相关状态，不能留下旧高亮。悬浮单条关系可以临时收窄高亮，移开后必须恢复原来的字段关联集合。

保留“选择”和“聚焦”的区别：画布普通点击不应每次强制跳动相机；目录的明确定位动作才调整视角。

### 验收

- 50 字段表的中间行和末行，在 800×600、1440×900 视口都能定位到可读位置。
- 同一字段有多个条件 net，从三个入口选择，关联集合一致。
- 数字 0 ID、复合关系字段也能定位。
- 目标行已在当前投影中时，定位不调用布局 Worker；尚未投影时，只允许一次必要的范围布局。后续平移/缩放不重复计算，也不改变模型保存时间。
- 三个子表引用同一主键：只选择其中一个子表外键时，其他两个兄弟分支不应被当成该字段的关联；选择主表被引用字段时则可以标亮全部真实关联。
- 新选中对象到来后，旧的异步聚焦结果不能把相机拉回去。

先补 camera/selection 纯函数测试。阶段末只验证一次“长表定位＋多关系字段选择”的 UI，不跑不相关保存、导入、导出脚本。

## S06. 徽标几何、颜色刷新与缓存一致性

### 已确认的两个边界

1. “混合”徽标宽 46，水平中心固定偏移 19，必定进入表框 4 个单位。
2. refreshLayoutContent 更新了 nodes/nets，未同步 domains，改组色后卡片与线可能不同色。

入口：

- [cardinality](../desktop/eda/cardinality.mjs)
- [CardinalityLayer](../desktop/eda/CardinalityLayer.jsx)
- [layout-quality](../desktop/eda/layout-quality.mjs)
- [layout-content](../desktop/eda/layout-content.mjs)
- [缓存编解码](../desktop/eda/layout-snapshot.mjs)
- [缓存指纹](../desktop/build/layout-cache-version.mjs)

### 固定决策与顺序

1. 抽取唯一的徽标尺寸/锚点计算，渲染器、碰撞检测、缓存几何签名共用。
2. 水平外移距离 = 徽标半宽 + 间距；垂直外移距离 = 半高 + 间距。
3. 先验证四边徽标不会进入表框，再考虑缓存失效；重排不能修复错误的锚点公式。
4. 用端口全部关系确定稳定的最大徽标包围盒和锚点。选择/悬浮只改显示值及高亮，不缩放徽标几何，也不进入缓存键。同尺寸的模型基数 1↔N 改动可以复用几何；统一值→混合等最大尺寸变化才触发必要更新。
5. 刷新 domains 及依赖它的线色；颜色变化不应重排整图。
6. 缓存恢复后，质量诊断必须与当前徽标/标签几何一致，不能保留旧的零遮挡结论。
7. 强制整理要取得最新模型内容，不能沿用按几何键冻结的旧展示元数据。
8. 不把所有 model 对象变化直接放进布局 effect 依赖来“修复”旧数据，否则注释每输入一个字又会启动布局。
9. 新的几何 helper 加入构建指纹；升级后只需一次失效，不能每次重开都失效。
10. 不存整份模型快照、不清空用户模型数据库、不把相机移动当作保存。

### 关键夹具

| 场景 | 预期 |
|---|---|
| 两条关系共享端口，1 变为混合 | 徽标变宽但不入表；质量结果与实际一致 |
| NORTH/SOUTH/WEST/EAST 各一个混合徽标 | 都在表框之外 |
| 1 与 N 互换但几何尺寸不变 | 文字刷新，允许命中缓存 |
| 选中、悬浮或取消混合端口的单个成员 | 只改文案/高亮，最大包围盒稳定，不启动 Worker |
| 只改组色 | 节点和线同时换色，不重新布局 |
| 只改名称/注释/枚举说明 | 最新内容显示，坐标不变 |
| 主动整理一次 | 本次绕过缓存，后续重开可复用 |
| 缓存损坏、版本过期、写入失败 | 重算或内存回退，不改模型 |
| 切模型后旧 Worker 返回 | 不覆盖新图、不写成新模型缓存 |

运行 cardinality、four-side-ports、layout-cache、layout-optimization 测试。
可与 S05 的视觉检查合并验证一次徽标/颜色，无需另跑全套 UI。

      "kind": "doc",

    }

1. 一行代表什么，是否混了两种职责？
2. 业务唯一性/幂等范围是什么，有什么约束证据？
3. 值来自哪里，是事实、估算、缓存还是派生？

5. 关系基数、条件、可选性为什么成立？

## S08. 统一可读性约束，补全冲突计数

### 现状

[metrics](../desktop/eda/metrics.mjs) 只统计不同 net 的线段内部横纵交叉。
异网共线和 T 形接触可能得到 crossings=0；部分线与非所属标签冲突未计入质量。

### 先定义“允许”，再写检测器

**不能因为坐标相同就认定真实连接。**

- 同 net、经真实共享端口或 Hub/Junction 的 Bus 干线共享：允许。
- 不同 net 在同一个真实语义端口，或投影明确声明的同一聚合端口组结束：允许在该端点接触，不自动允许整段共线。聚合组必须能追溯到成员字段/端口；不能仅凭坐标相同临时认定为聚合。
- 不同 net 的中途共线重叠：报告异网共享冲突。
- 没有共享端口/节点身份的 T 形接触：报告非法接触。
- 正常十字交叉：计为 crossing，不画成 junction。
- 线穿本关系标签与线穿其他关系标签要区分；至少禁止非所属标签被穿过。
- 条件标签、1/N 徽标、Bus 数量标签都进入几何检查。
- 固定 UI 小地图不属于数据库连接关系；不要把它加入语义 net。

### 排序决策

先形成明确的 candidate validity，再比较代价：

1. 必须保留节点/关系身份、有效坐标、正交路径和指定相对位置。
2. 不穿表，不遮关键标签/徽标，不产生非法接触或异网共线歧义。
3. 在满足以上条件的候选中，仍然按交叉数优先，再比较线长、转角和紧凑度。

这是把“不可读”作为不可行条件，不是任意推翻用户此前的交叉优先目标。

- 所有基础候选和改良候选共用同一个可行性函数。
- 如果没有满足条件的候选，不得清空问题计数冒充成功。
- 若选择返回便于修复的降级图，必须明确标成 degraded 并带诊断；不得作为正常成功缓存。
- 原模型不得因找不到好布局而被修改、删除或回滚到别的模型。

### 必须新增的独立小夹具

| 夹具 | 预期 |
|---|---|
| 正常十字交叉，两个不同 net | crossings > 0，无假 junction |
| 两个不同 net 中途共线 | 共线冲突 > 0 |
| 无共享语义身份的 T 接触 | 非法接触 > 0 |
| 合法 Bus 共享干线 | 不误报非法共线 |
| 同坐标但不同语义端点 | 不能自动算连接 |
| 领域摘要将多个字段明确聚合到同一端口组 | 允许声明的端点接触，不误伤现有领域视图 |
| 线穿其他关系的条件标签 | 标签冲突 > 0 |
| 宽徽标/Bus 数量标签挡住元素 | 冲突可检测 |
| 0 crossing＋遮挡 vs 1 crossing＋可读 | 选择可读候选 |
| 所有候选不可读 | 明确失败/降级，不报告完美图 |

不要在此阶段引入新布局库。主要运行 metrics、layout-quality、cardinality 的纯函数测试。

## S09. 候选容错与共享预算，不再丢弃已经算好的图

依赖 S08 的统一可行性。入口：
[layout](../desktop/eda/layout.mjs)、[refinement](../desktop/eda/refine-positions.mjs)、[compaction](../desktop/eda/compact-layout.mjs)、[worker task](../desktop/eda/layout-task.mjs)。

### 固定决策

- 每个基础候选单独捕获异常；后一个失败不能推翻先前有效候选。
- 前置布局、端口搜索、SPOrE、局部移动使用同一个预算/截止时间。
- 保留外层约 25 秒硬保护，首次进入布局时生成共享软 deadline，并为最终消息传回预留时间。可选优化的 6 秒上限只能进一步收紧预算，不能每层重新计时延长总预算；用可注入时钟写测试，不真的等待 25 秒。
- 不先等待四个压缩候选全完成，再检查预算是否已用完。
- 截止时返回**本次请求**已经验证的最佳结果；没有有效结果才失败。
- 用户取消、切模型或改变结构后，不发布迟到结果。
- 不能拿上一个模型或旧几何的图冒充本次成功。
- 有效基础图可先显示；继续优化时保留相机/选择，不在用户操作中跳图。
- 若实现 Worker progress 消息，必须显式区分 progress 与 final；现有 promise 不得把 progress 当最终结果。
- 缓存只保存已验证、与当前指纹匹配的可用结果，不保存半成品。
- 已验证的基础候选可以在超时回退被正式选中后缓存；仅收到 progress 消息不立即写缓存。未通过 S08 可行性检查的 degraded 图不能进入正常缓存。
- 超时后若要提供有效回退，必须在 Worker 被终止前传回，不能指望终止后读取其内存。
- 取消与超时不同：显式取消返回取消状态，不趁取消应用迟到候选；超时可选择本请求已传回且验证通过的最佳候选，并标明优化未完成。

### 受控引擎夹具

- 第一个成功、第二个抛错：保留第一个有效结果。
- 全部失败：返回明确失败，不产生伪图。
- 初始布局成功、优化超时：返回可用初始结果及停止原因。
- 在压缩前预算已耗尽：不启动压缩。
- 执行中取消、随后旧结果到达：不显示、不覆盖缓存。
- A 模型任务迟到、当前已切 B：B 不受影响。
- 一次请求的 progress/final ID 不匹配：忽略。
- 相机移动不改变布局请求身份，不触发自动重排。

### 规模优化放在本步正确性通过之后

当前 80 的门槛是投影节点，包含虚拟节点，不是表数。
保留“42 表、81 关系、40 junction、共 82 节点”的合成夹具。

先记录阶段耗时、真实/虚拟节点数、可行候选数与回退原因，再决定预算分配：

- 优先保留低成本端口调整；
- 大规模候选按连通块/领域或局部问题分配预算；
- 总图仍显示全部表；
- 不直接把阈值从 80 改到 500，也不承诺全局最优。

本步不默认做大型 UI 压测。只有测量表明拖动/缩放有问题，再检查相机更新、全图索引重复创建和视口裁剪；不直接换 WebGL。

## S10. Agent 完整闭环：读取、校验、替换、确认

不设计局部 patch；不引入 Agent 编排框架。复用 S04 请求和回执。

### 拟新增的只读入口

例如 --export-model <明确输出文件> --model-id <当前模型ID>，以及查询当前模型身份的能力。
这些是目标接口，具体落到现有 CLI/bridge 体系，不另开 HTTP 服务或调试端口。

固定规则：

1. 返回当前工作区模型及 ID，不能静默切到别的模型。
2. 明确返回的是 React 中已提交的当前工作内容，可含尚未保存的修改；不是随意选择磁盘旧副本。
3. 若存在未应用或无效输入草稿，应返回明确的草稿状态/错误；不自动 blur、保存或丢弃用户输入。
4. 只读动作不触发保存、替换、整理或清空撤销栈。
5. 输出路径必须由调用方明确指定；已有文件默认不覆盖，显式 overwrite 才允许。
6. 保持现有 20 MB 边界和可信 frame 检查，不加入任意脚本执行能力。
7. 人类仍使用桌面 UI，不要求人类操作这些命令。

### 防止 Agent 覆盖读取之后的人类修改

- 读取时返回当前**模型内容**的 contentHash。
- 替换可携带 expectedContentHash；不匹配就拒绝，要求重新读取。
- contentHash 排除相机、阅读状态、保存时间、缓存和备份元数据。
- 规范化对象键顺序，但保留表/字段/索引字段等数组的有意义顺序。
- 文件 sha256 是传输文件的字节校验，不等于 contentHash，不能混用。
- 这是一次操作的并发保护，不是模型版本历史或评审基线。
- 保留现有“替换执行过程中内容变化”的事务检查，不用新 hash 取代它。
- 对未提供 expectedContentHash 的旧调用保持兼容，但文档明确其保护范围较弱。

### 状态确认

沿用“模型已应用”和“布局完成”两个状态，不混淆：

- 模型成功但布局仍在计算：模型操作 succeeded，layoutStatus 为 pending。
- 命中匹配缓存或本次布局完成：layoutStatus 为 ready。
- 模型已应用但布局失败/降级：明确 layoutStatus 与原因，不谎报模型未提交，也不自动回滚。
- 只能用 requestId、modelId 和几何身份匹配本次渲染完成事件，不能用固定 sleep 推定成功。
- 在未实现布局完成观测前，返回 not_observed，不能伪装 ready。

### 验收

使用内存 bridge/存储和虚构模型覆盖：
读取不写模型；输出目标冲突；含未保存内容；未应用草稿；hash 相符/不符；
读取后仅移动相机不冲突；读取后字段被人改动必须冲突；
成功替换不换 ID、不增加模型副本；布局 pending/ready/failed 不串请求。

完成后只需一次针对性的“读取→预检→全量替换→确认”集成验证。
不要再执行所有旧 UI 冒烟脚本作为收尾仪式。

## 11. 测试与验收总规则

### 11.1 测试分层

| 改动 | 默认验证 | 何时补 UI |
|---|---|---|
| 条件/契约/SQL/评分/缓存纯逻辑 | 定向 Node 测试 | 有无法由纯逻辑覆盖的集成疑点时 |
| 构建注入、IPC/bridge | 锚点/消息契约测试＋构建 | 跨进程应用链路发生实质变化时一次 |
| 字段定位、高亮、徽标、详情布局 | 纯函数测试＋构建 | 阶段末一次代表性视觉/交互检查 |
| 发布 | 用户授权后走 CI、扫描、打包校验 | 按发布风险选择，不重复所有开发验证 |

本轮实施过程中不默认执行 npm test 的全部套件。
准备公开发布时，再按项目 CI 要求执行完整检查。

### 11.2 真实可用的命令示例

以下现有测试文件在基线仓库中存在。每步只选相关文件；新测试创建后才加入命令。

- 确认命令实际运行了目标测试并输出非零数量；不要只看进程退出码。
- 不因测试失败就放宽断言。只有行为契约确实改变，才更新旧断言，并写明理由。

- 做 UI 验证时使用隔离的虚构工作区，不操作用户正在编辑的模型。
- 未跑 UI、未测某平台必须如实说明；源代码分析不等于运行验收。
- 拆分过大的源码/测试文件时，按仓库约定用 jscpd 等成熟工具扫描新旧文件并消除有意义的重复。

### 11.3 必须停止并报告的情况

1. 无法判断一个关系是不是物理 FK：保留 unspecified，不猜测；如任务要求实际落库语义，向用户确认。
2. 发现真实模型、内部资料或凭证混入公开源码/测试/产物：停止发布相关步骤，不扩大上传范围。
3. 必须覆盖不属于本次工作的未提交修改、删除模型或批量改写业务元数据：停止。
4. 拟引入模型历史/审批、局部 patch、新绘图库、Agent 框架或数据库执行能力：超出本计划，停止扩展。
5. 为通过检查必须移除安全校验、忽略非法条件或隐藏表/关系：停止，修根因。
6. 无法通过已有权限完成安装/发布：完成可做的本地部分，说明具体权限缺口；不能绕过限制。
7. 基线与当前代码差异很大，方案已不适用：先更新差异说明，不强行套旧锚点。

普通 UI 文案、辅助函数名称、局部样式不属于停止条件。

### 11.4 不得顺手做的事情

- 自动 push/merge、修改远端标签或发布安装包。
- 每一步生成一个新 App 副本、重启用户 App 或导入真实数据。
- 为“优化布局”改表结构、关系方向、ID 或业务分组的实际含义。
- 自动把所有关系标为 physical，或把非法条件当作没有条件。
- 为减少空白隐藏表，或通过把字体缩小到不可读来宣称布局完成。
- 把“没有检查出问题”改成“业务评审通过”。
- 用截图正常、构建成功或 CI 通过代替没有执行的语义验证。
